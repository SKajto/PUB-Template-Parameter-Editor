# GPLv3 source and binary release instructions

> [!NOTE]
> **Channel update, 2026-10-26 (owner decision).** This application is **not** distributed through
> the Microsoft Store: no Store product or identity is reserved, and no artifact of this project is
> Store-signed. The shipped artifact is the self-contained single-file
> `PUB_Template_Parameter_Editor.exe` attached to a GitHub Release, signed by SignPath.io with a
> certificate by SignPath Foundation. The MSIX packaging in `packaging/` remains as local tooling.
> Current wording: [docs/RELEASE_PACKAGING.md](RELEASE_PACKAGING.md) and

Fresh project licensing baseline, 25 October 2026. Use GPL version 3 for the new GitHub application. GPL-3.0-only is the provisional SPDX choice unless the owner explicitly selects GPL-3.0-or-later. GPL-3.0-or-later grants an additional version choice and must not be silently substituted. This document is an engineering release checklist derived from the license, not a blanket determination of every possible Store agreement.

## Repository and application notices

- Add the unmodified full applicable GPL text in the actual app repository's LICENSE, accurate copyright notices using the real holder/year, and matching SPDX/source/metadata identifiers. Do not invent copyright ownership.
- Include accurate attribution and dependency/asset notices. The app's GPL license does not relicense .NET/WPF or other bundled components. Include their actual applicable license/notice texts as required and inventory what is shipped.
- Embed or package the app license, warranty/copyright notices and third-party notices, accessible offline from About/Licenses. The portable profile can embed those resources without shipping a separate runtime file.
- About shows app/package version and the exact source release URL; Store metadata points clearly to corresponding source and license terms. Do not add app EULAs that prohibit modification, reverse engineering or redistribution contrary to GPL rights.

## Corresponding source release practice

For each distributed binary, publish a no-charge source archive for the exact commit/tag. Include the application's source, UI resources, project files, manifests, build/installation/packaging scripts and any required generated or submodule inputs. A default-branch link alone can drift away from the distributed release. Audit required dependencies and how their source/license obligations are met; do not automatically classify every bundled component as an exempt system library.

Document supported SDK/tool versions, restore/build/test commands, a portable build path and an MSIX packaging path. A recipient must be able to build/modify the software without the maintainer's Store account or release secrets. Clearly distinguish producing an independent build from publishing an official update under the maintainer's reserved Store identity. Do not require recipients to use Microsoft's signature or the maintainer's credentials to build the app.

GPLv3 section 6 permits a different network server for corresponding source when the binary distribution clearly directs users to it and equivalent access is maintained. Use GitHub releases/source archives accordingly: place clear directions in the Store listing and in-app About, retain release assets and links, and make the source available for the required distribution period. Include complete required inputs; autogenerated GitHub archives may omit submodule contents.

Exclude secret credentials, private certificates and uncleared proprietary template data from the public source archive. Use redistributable/sanitized fixtures while preserving meaningful tests. If a required build input cannot be distributed, resolve that concrete problem rather than calling an incomplete archive corresponding source.

## Store and GPL boundaries

Package signing for authenticity is not by itself a blanket finding that GPL distribution is impossible or automatically compliant. Review the actual applicable distribution/license terms, preserve GPL-granted rights, and don't add app-enforced Store-only execution, DRM or trial restrictions that conflict with those rights. Evaluate any GPLv3 Installation Information obligation for the actual distribution arrangement when relevant; don't assume every desktop app release automatically requires disclosing Microsoft/private signing keys or that a second download channel cures a conflicting term.

Document how recipients can build and run modified versions in an independently authorized Windows environment, including their own package identity where needed. Store submission/signing credentials are release-service secrets, not general source-build prerequisites. Record any concrete unresolved licensing conflict before the relevant release; continue ordinary engineering work that does not depend on that issue.
